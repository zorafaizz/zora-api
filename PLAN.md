## 2. Storage and execution architecture
Use PostgreSQL as durable source of truth. Use a supported version compatible with deployment; inspect existing installations before choosing. Use a bounded connection pool per process and calculate aggregate connections across workers. Use migrations, foreign keys, unique constraints, CHECK constraints, transaction isolation and indexes justified by EXPLAIN. Use integer credits (BIGINT) and integer IDR amounts, never floating-point money. Serialize large integers safely in JSON. Store timestamps in UTC; define quota day in Asia/Jakarta. Redis is for cache, distributed limits, ephemeral coordination and BullMQ, never authoritative balances. Separate queue Redis from evictable cache if memory pressure warrants it; queue Redis must not evict job keys. Configure authentication, private binding, persistence, backups and recovery appropriate to each service. No public database or Redis ports.

Use Express existing, PM2 cluster for stateless HTTP workers, and separate bounded BullMQ worker pools for CPU-heavy media, browser/scraper and billing/reconciliation. Choose worker count from measured CPU/RAM, not blindly all cores; account for Sharp/libvips threads, browser processes and queue workers. Benchmark before/after. Use PostgreSQL transactional outbox to bridge durable jobs/events to Redis; idempotent consumers and recovery scans. Avoid holding DB transactions during upstream calls. Handle SIGTERM, drain, job leases and worker crashes. Keep infrastructure minimal; do not introduce Kubernetes or distributed databases without measured need.

## 3. Identity and API keys
Implement account authentication with Google OAuth/OIDC using a maintained library, secure session cookies, CSRF protection, state/nonce/PKCE where applicable, verified identity and unique provider subject. Do not require Gmail access or sensitive scopes. OAuth credentials are optional until configured; provide documented local test auth only in isolated nonproduction environments. Never enable a production auth bypass.

Brand API keys as Zora Key unless existing naming requires a compatible alias: `zora_test_<public-id>_<secret>` and `zora_live_<public-id>_<secret>`. Generate at least 256 bits of random secret using CSPRNG, store HMAC-SHA256 digest with server-side pepper and key identifier, constant-time comparison, reveal plaintext once, redact from logs and URLs. Support rotation, revocation, expiry, scopes, labels and last-used timestamps. Support Authorization Bearer and legacy transport only where required; discourage query-string secrets. Test keys must not access live billing or production-only resources. Account ownership is checked for every key management action.

### Quota rules (mandatory)
- TEST: exactly 50 successful eligible requests total per account, lifetime, one allocation only. Multiple test keys, revocation, regeneration or rotation must not reset or multiply this allocation. Test requests use sandbox fixtures where practical; explicitly mark any real upstream execution and apply resource caps. Test access to expensive endpoints may be restricted or use bounded fixtures, clearly documented. No real top-up via test key.
- LIVE: 20 free successful eligible requests per account per calendar day (Asia/Jakarta), shared across all live keys. No rollover. Paid credits are separate. Free request allowance is a count, not 20 credits. Define eligible endpoints explicitly; expensive endpoints can be paid-only or have a bounded free variant. Default use eligible free allowance first, then paid credits only if account/key permits paid fallback. Expose settings and clearly disclose charging before execution. Do not charge failed provider executions; rate-limit rejected and failed attempts separately to prevent abuse.
- Inactivity: after 5 consecutive days (120 hours) without a qualifying authenticated successful LIVE API request, temporarily freeze only the free benefit. Do not freeze paid credits, paid API access, login, key management or account ownership. Track last qualifying activity; for never-used accounts use activation time. Do not let health checks, test keys, invalid calls or dashboard polling count. Use lazy evaluation plus periodic reconciliation, no daily mass reset required. Reactivation policy proposed: verified dashboard session, explicit reactivation, risk assessment, then restore remaining current-day allowance without issuing extra quota; suspicious accounts require review. Document this assumption and make configurable. Paid successful activity can update last activity but must not silently grant a frozen benefit; explicit reactivation remains required. Ensure no race between freeze, reactivation and requests.
- IP whitelist per key: optional IPv4/IPv6 CIDR allowlist, disabled by default; validate canonical IPs and IPv4-mapped IPv6, support multiple ranges, audit changes, reject mismatches before billing. Trust forwarding headers only from explicitly configured reverse proxies; never trust arbitrary X-Forwarded-For. Provide preview and recovery via authenticated dashboard to prevent lockout. Do not expose private IPs in public logs.

## 4. Anti-farming and account routing defense
Goal: prevent mass account creation and pooling/rotation of free keys while minimizing harm to legitimate users sharing NAT, mobile networks, VPNs, proxies or Pterodactyl nodes. Do not claim perfect identity detection. Never equate one IP with one person. Never block a shared hosting IP merely because multiple accounts use it. Do not attempt invasive device fingerprinting, cross-site tracking, collection of contacts, or covert surveillance. Collect only proportionate first-party security signals, document purpose, retention and deletion; restrict access and avoid logging raw secrets or request bodies.

Implement separate signup risk, account risk, key risk and request risk. Signals: verified OAuth subject uniqueness, account age, signup bursts, free quota exhaustion followed by rapid key switching, repeated correlated endpoint sequences and timing, repeated unusual usage patterns, concurrent key usage across accounts, repeated first-party session/device identifiers where available and disclosed, IP/ASN/network class as weak context, and confirmed abuse history. Mobile IP rotation and proxies are not proof. Shared IP alone must never trigger account linkage or suspension. Do not infer identity from protected traits. Use pseudonymized keyed hashes for correlation where feasible; limit retention and avoid storing full payloads. Never require a paid identity vendor or external fingerprinting service without approval.

Design a bounded account-correlation graph: accounts/keys as nodes; time-decayed evidence edges with provenance, confidence and independent signal families. Avoid transitive guilt: A related to B and B related to C does not prove A=C. Downweight high-degree shared network nodes, hosting ASNs, common endpoint patterns and widely shared infrastructure. Require multiple independent strong signals for high-confidence clusters. Detect key rotation patterns using sliding windows and sequence similarity over endpoint IDs/time buckets, not sensitive query contents. Distinguish legitimate multi-tenant panel traffic from coordinated quota harvesting. A single API key used from many IPs is not automatically abuse. Use explainable rules and configurable weights first; no opaque ML or automatic permanent bans. Record reason codes, evidence timestamps, confidence and rule version. Provide admin review and appeal, expiry of sanctions and allowlisted legitimate organizations. Avoid leaking exact detection thresholds publicly.

Enforcement ladder: observe → throttle signup or free-benefit issuance → step-up verification/CAPTCHA on suspicious signup/reactivation → temporary free-benefit hold on correlated accounts → manual review → revoke confirmed abusive keys/accounts as justified. Paid traffic remains available unless actual security abuse warrants restriction. Use IP limits only for volumetric attacks with short TTL, generous shared-network budgets and exceptions; never globally blacklist Pterodactyl nodes based on farming suspicion. Use account/key-level token buckets, endpoint budgets and concurrency limits. Add signup rate controls across multiple signals, not IP-only. Keep false-positive metrics and shadow mode before enforcement. Risk thresholds must be configurable and tested against legitimate shared-IP scenarios. If Redis/risk engine is unavailable, avoid granting unlimited free quota; use durable DB checks and safe degraded policy without blanket IP bans.

Acceptance scenarios: 100 legitimate accounts behind one panel IP remain usable; mobile IP changes do not reset account quota or trigger ban alone; one user rotating 20 keys cannot exceed account quota; simulated coordinated accounts with repeated independent signals trigger free-benefit review; unrelated accounts sharing an ASN remain independent; a compromised key can be revoked without affecting unrelated accounts; appeals and expiry work. Test false positives and document detection limitations.

### Accounting invariants
- Separate paid credits, free daily request count and lifetime test count. Wallet available/reserved balances nonnegative; append-only ledger with unique operation references, actor, reason, amount and timestamp. Prefer double-entry credit postings or equivalent auditable balanced accounting; explicitly define invariants and reconciliation.
- Reserve → execute → capture/release. Atomically reserve paid credits with conditional UPDATE and insert reservation/ledger in same DB transaction. For free/test, reserve quota count atomically in durable bucket with unique account+period; finalize on success, release on failure. Do not permit concurrent overdraw. Capture only once; release only once; use state transitions and row locks/conditional updates. Snapshot price version and quota source per request. Do not switch free/paid silently after execution starts.
- Idempotency scoped to account, endpoint and request fingerprint; same key with different payload returns conflict. Persist outcomes or job references for safe replay. Do not double-charge retries, provider fallback or duplicate queue deliveries. For side-effecting upstream calls use upstream idempotency or reconciliation, not blind retries.
- Reservation expiration must not release an actively running job: use leases/heartbeats, fenced ownership or equivalent state transition guards. Reconcile unknown outcomes; ensure late worker cannot capture a released reservation. Commit billing result before reporting success; handle lost client connection and document policy. Define billing success as usable endpoint result, not merely HTTP 200. Cache hits are billable according to published endpoint policy; never charge multiple times for one logical request.
- Payment fulfillment: verified provider event, exact invoice amount/currency/order mapping, unique provider transaction/event IDs, monotonic status transitions, atomic invoice paid + credit grant + ledger + outbox. Handle duplicates, out-of-order notifications, refunds and chargebacks with compensating entries, not ledger edits. No real gateway implementation now.
- Expose authenticated balance, usage, pricing, invoices, ledger and SSE events. SSE is notification only; reconnect fetches durable snapshot. No user can access another account's data. Return documented rate/credit headers and 402 for insufficient paid balance where appropriate.

## 6. Flexible resource-based pricing
Do not hardcode one credit per endpoint or assume VPS resources are free. Implement versioned pricing registry with fixed prices per endpoint or resource tier and optional metered prices for predictable variable workloads. Measure CPU time, peak/incremental memory and memory-time (GB-seconds), execution duration, egress bytes, storage duration, upstream paid API costs, browser occupancy and retry overhead. Use process/container or isolated worker measurements for attribution; do not treat whole-process RSS delta as accurate per-request usage under concurrency. Use representative benchmarks (cold/warm/cache hit, small/large inputs, concurrent load) and store p50/p95 costs. Never claim measured values without measurements.

Cost model in IDR: allocate monthly VPS cost to usable CPU core-seconds and RAM GB-seconds using explicit cost weights that sum to 1, realistic utilization and headroom; add attributable bandwidth/storage/provider costs and operational overhead. Avoid double-counting shared fixed costs. Compute target price = estimated cost / (1 - target gross margin), then convert to integer credits with rounding up and minimum floor. Include payment fees and taxes where applicable once actual terms are known. Configure credit sale value, margin, minimum price, free subsidy budget, cost weights and price ceilings; do not invent final commercial prices. Report assumptions and sensitivity. Keep public prices predictable: publish fixed tiers for cheap endpoints and input-size/resolution/model-token bands for expensive ones; quote maximum charge before execution, reserve max, capture actual bounded cost, release remainder. Never exceed accepted quote without new consent. Price versions immutable for historical usage; changes take effect prospectively and are auditable. Cache hits may have a published lower price or same price; choose explicit policy. Free requests remain counts, not credits, and expensive endpoints require explicit eligibility/caps.

Example classes (illustrative, not final prices): lightweight cached data; network scraper; multi-provider/browser scraper; media conversion; UHD upscale; AI token-metered; storage/egress-heavy. Produce `docs/pricing-model.md`, benchmark data, configurable pricing seed and admin price preview. Include per-endpoint resource ceilings (max pixels, bytes, duration, tokens, concurrency) to prevent loss-making requests. Test rounding, zero/negative input, overflow, version changes and refunds.
